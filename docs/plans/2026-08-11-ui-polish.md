# UI/UX polish plan

**Date:** 2026-08-11
**Status:** complete except item 8, which was deferred by the owner
**Source:** live audit of `main` at `e82d28f`

## Why this plan looks the way it does

It was not brainstormed. Every item below came from driving the running app and
measuring, and the ones that were *not* found are recorded too.

That method was chosen because of what happened the day before. The calendar
branch went through fifteen reviewed tasks, a separate whole-branch review, a
six-finding fix wave, and 147 passing tests. Three real defects still reached
the branch, and every one needed a rendered DOM to find: a filter badge that
read "1" with nothing filtered, a week lens truncating names to a few
characters in the one view built to show them in full, and a year lens that
moved its focus ring without moving focus. The same session then found that
**no date could be set on any field of the item form** — a bug that had been
live in the shipped app, invisible to every test in the repo.

Reasoning finds correctness you can reason about. It does not find pixels,
hit tests, or focus. So: measurements, or it does not go in the plan.

### Method

Each surface was visited in the running app at 1280×900, 1024×768, and 820×700,
in both themes, with a harness that measured per view:

- page and element overflow past the viewport
- text clipped by its own box (`scrollWidth > clientWidth`)
- hit targets under the WCAG 2.2 minimum of 24×24
- interactive elements with no accessible name
- ARIA roles used outside a valid container
- duplicate ids, unlabelled inputs, heading-level skips
- focus indicators, measured by pressing **real** Tab keys and diffing computed
  style against a pre-focus baseline

Surfaces: Dashboard, Calendar (week/month/year), Subscriptions, Bills,
Analytics, Settings, and the item form in both add and edit modes.

### One correction, recorded on purpose

The harness first flagged a 1px-wide element on the Dashboard holding "Showing
top 6 categories" — apparently invisible text. It is a deliberate
`aria-live="polite"` region using the standard visually-hidden pattern, and is
supposed to be 1×1. The harness was wrong, not the code. Anyone re-running this
audit should exclude `clip: rect(0 0 0 0)` elements before believing a clipped-
text result.

## What is already healthy

Recorded so nobody spends a day re-auditing it.

- **No horizontal scrolling anywhere**, on any surface, at any of the three
  widths. The responsive story is genuinely solid down to 820px.
- **No ARIA role-context violations app-wide.** Every `gridcell` sits in a
  `row`, every `row` in a `grid`, and nothing claims `menuitem*` outside a
  menu. This was checked specifically because the calendar shipped that exact
  bug three times during development.
- **No duplicate ids.** No heading-level skips.
- **17 of 18 controls tabbed through do show a focus indicator.** The failure
  below is contained to one component, not systemic.
- **The item form is structurally sound**: the dialog is named and
  `aria-modal`, no control is under 24×24, no input is unlabelled, no button
  is unnamed, and a failed submit correctly moves focus to the first errored
  field.
- Live regions exist and are correctly hidden.

## Findings

Ranked by how much they cost a real user, not by effort.

### 1. The search/filter/sort toolbar is invisible to keyboard users

**Where:** `SearchFilterToolbar.tsx` — appears on both Subscriptions and Bills.

**Evidence:** Pressing real Tab through the toolbar, three of its five controls
show no focus indicator at all: the search input, the Filter button, and the
Sort button. `:focus-visible` matches; the computed outline is
`none 3px rgb(163,163,163)` — `outline-style: none` renders nothing regardless
of width and colour.

**Cause is the interesting part.** The stylesheet already defines the ring:

```css
.search-shell button:focus-visible { box-shadow: inset 0 0 0 2px var(--brand-primary); }
```

Those three controls carry inline `style={{ boxShadow: "none" }}`, and an
inline style beats a stylesheet rule. The design intent exists and the
implementation silently cancels it. The Grid/List buttons have no inline
override and do show the ring, which is why the bug reads as random rather
than total.

**Fix:** Drop the inline `boxShadow: "none"` from the three controls and let
the stylesheet rule apply. Add an input rule alongside the button one — the
current CSS only covers `button:focus-visible`, so the search field would
still have nothing.

**Effort:** small. **Risk:** low — it only adds a ring where none renders now.

### 2. Selection checkboxes are 16×16

**Where:** Subscriptions and Bills list rows — one per item.

**Evidence:** measured 16×16. WCAG 2.2 (2.5.8) sets a 24×24 minimum. Ten
instances on Subscriptions, three on Bills, scaling with the list.

**Fix:** keep the 16px visual box, expand the hit area to 24×24 with padding
or a pseudo-element. The control need not grow for the target to.

**Effort:** small.

### 3. Search inputs have no accessible name

**Where:** Subscriptions and Bills.

**Evidence:** the only naming is `placeholder="Search subscriptions..."`. A
placeholder is not a label — it is announced inconsistently and disappears on
first keystroke, so a screen reader user who tabs back to a half-typed query
hears nothing about what the field is.

**Fix:** `aria-label` on the input. Visible label would cost layout in a
composed toolbar; the aria-label is the right trade here.

**Effort:** trivial.

### 4. Required fields are starred visually but not marked programmatically

**Where:** item form — Name, Amount, Start Date, Next Billing.

**Evidence:** all four render a `*` in their label. All four report
`required: false` and no `aria-required`. The requirement is conveyed by a
glyph and by nothing else.

**Fix:** `aria-required="true"` on the four. Prefer `aria-required` over the
native `required` attribute so the form keeps its own validation and shake
behaviour rather than triggering the browser's.

**Effort:** trivial.

### 5. The Amount field says it is invalid without saying why

**Where:** item form.

**Evidence:** submit empty. Both Name and Amount get `aria-invalid="true"`.
Name also gets `aria-describedby="item-name-error"` pointing at "Name is
required". Amount gets `aria-describedby: null` — its message, "Enter a valid
amount", is rendered on screen but associated with nothing. A screen reader
user hears "Amount, invalid" and no reason.

The inconsistency is the tell: one field is wired correctly and the other is
not, so this is an omission rather than a design decision.

**Fix:** give the amount error node an id and point `aria-describedby` at it,
matching what Name already does.

**Effort:** trivial.

### 6. ~~Analytics truncates the names it exists to show~~ — WITHDRAWN

**Status: could not be reproduced. Do not act on this.**

The original entry claimed `The Wall Street Journal` was given 115px of the
169px it needs in "Most Expensive Commitments" at 1024px and below. Re-measured
in the signed-in app, nothing in that panel is clipped at any width tried:

| viewport | grid | names get | clipped |
|---|---|---|---|
| 1024 | one column (`xl:` is 1280) | 376px | none |
| 1280 | two columns | ~483px | none |
| 1360 | two columns, 503px each | ~390px | none |

Ruled out, in order: a layout change since the audit (the grid class is
untouched — only colour tokens moved in that file); the `xl` breakpoint
flipping column count; and the view's entry animation, by sampling at 150ms,
400ms, 800ms, 1.5s and 2.5s after switching to Analytics. Every sample came
back empty.

Two things were wrong with the original finding. It named
"Most Expensive Commitments" without confirming which card those elements sat
in — the harness reported a bare `p.truncate.font-medium` and the panel was
inferred. And the items it named, `Tombigbee Fiber` and `The Wall Street
Journal`, do not rank into a panel led by Housing at $650/mo, so they were
probably never in that card at all.

Left here rather than deleted, because "a finding that could not be reproduced"
is worth more to the next person than a silent gap. If it resurfaces, capture
the containing card and the sidebar width at the same moment.

### 7. The sidebar seam toggle is 23×23

**Evidence:** 1px under the 24×24 minimum, on every surface.

**Fix:** one pixel of padding. Listed for completeness, not urgency.

**Effort:** trivial.

### 8. No `h1` on any surface — DEFERRED (2026-08-13, owner's call)

Still true: `h1` count is 0 on all six views, confirmed in the closing sweep.
Held because promoting each view's title restyles headings across the whole
app, and TASK-022's colour sweep is working the same surface. Pick it up once
that lands, on its own, with a look at each view after.


**Evidence:** every page starts its heading structure at `h2`. No level is
*skipped*, so this is well-formed but top-less: a screen reader user asking
for the page title gets nothing.

**Fix:** promote each view's title to `h1`. Check `--font-display` sizing does
not shift, since these are styled by inline rules rather than by tag.

**Effort:** small. **Risk:** visual — verify each view after.

## Explicitly out of scope

**Colour contrast.** `--text-muted` fails WCAG AA in both themes (2.18:1 light,
2.36:1 dark, at 11px). That is **TASK-022** and is being handled separately;
this plan does not touch it, and the two should not be merged into one pass —
TASK-022 is a token change with an app-wide regression sweep, while everything
here is local and independently shippable.

Also untouched: **TASK-023** (calendar polish), **TASK-024** (popover viewport
overflow at short window heights).

## Found after the plan was written

Running the harness on the **sign-in page** — a surface the original audit
never visited, because it only ever looked at signed-in views — turned up two
more:

- **The email and password fields have no accessible name.** No `id`, no
  `aria-label`, no wrapping `<label>`; the placeholder is all there is. Same
  defect as item 3, on the first screen anyone meets.
- **Three controls are 20px tall** against the 24px floor: "Show password",
  "Forgot password?", and "Sign up".

Neither is fixed yet. Add the sign-in and sign-up screens to the sweep for
items 2, 3 and 7 rather than treating them as separate work.

## Found while verifying, in the signed-in app

Once a pinned dev origin made the authenticated views reachable, two more
turned up that the original sweep could not have seen:

- **Settings had 28 unnamed buttons.** Every category row carries a hover-
  revealed Edit and Delete at 16×16 with no `aria-label` — announced as
  "button", nothing more, and one of them deletes. They are `opacity: 0` until
  the row is hovered but sit in the tab order the entire time. **Fixed**: named
  per category, skirted to 24×24, and revealed on `focus-visible` so keyboard
  users can see what they have landed on.

  The harness missed these because it skipped `opacity: 0` elements. That
  filter has been removed — it excluded precisely the controls least likely to
  be labelled.

- **The sidebar resize handle is 12px wide** (12×784). Named correctly, and
  easy to grab vertically, but under the 24px floor on its narrow axis. Not
  fixed; a drag handle is a different shape of problem from a button and widening
  it eats into the panel.

## Sequencing

Items 1, 3, 4, 5 are the accessibility cluster and share one file each. Doing
them together is one contained pass and closes every finding that blocks a
keyboard or screen-reader user.

Items 2 and 7 are hit targets — mechanical, do them together.

Item 8 carries visual risk and wants a look after the change.

**Recommended order:** 1 → 3, 4, 5 → 2, 7 → 8. (6 is withdrawn.)

Item 1 first on its own: it is the only finding here that makes a surface
unusable rather than degraded, and it is the one most likely to be reintroduced
by anyone editing that toolbar, since the inline style looks deliberate.

## The verification server

Findings here are measured in a browser, not in the Tauri window. The native
window cannot be captured — it runs as a bare executable with no bundle
identifier, so macOS's screen-capture filter excludes it from every
screenshot. Early in this work that produced a genuinely misleading session:
what got opened was the installed *release* build, showing old code.

`tauri dev` serves the same app over HTTP, so the browser is the way in. The
catch is the session: a browser tab is a different origin from the Tauri
webview, so it starts logged out, and a server on a random port starts logged
out *every time*.

Hence a pinned one:

```bash
bun run dev:verify     # vite on a fixed 1430
```

Sign in once at `http://localhost:1430` **in the browser being driven** and the
session persists in that origin's storage. Everything behind auth — the item
form, the Subscriptions and Bills toolbars, the calendar — becomes measurable
instead of inferred.

`PORT` rather than `vite --port` on purpose: `vite.config.ts` derives the HMR
socket and the dev CSP from that value, so a bare CLI flag would move the
server and leave the CSP pinned to the old HMR port — the page would load and
hot reload would quietly stop.

## Verifying this work

The harness that produced these findings should be re-run after, at the same
three widths and both themes. A fix that does not move its number is not a fix.
Specifically:

- Item 1: tab through the toolbar and assert a non-`none` outline or a changed
  box-shadow on all five controls
- Items 2, 7: assert zero controls under 24×24
- Items 3, 4, 5: assert zero unlabelled inputs, four `aria-required`, and an
  `aria-describedby` on every `aria-invalid` field
- Item 6: assert `scrollWidth <= clientWidth` on the commitments list at 1024
- Item 8: assert exactly one `h1` per view and no level skips
